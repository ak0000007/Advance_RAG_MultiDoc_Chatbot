1. Feature Overview

Feature Name & Subsystem: Persistent HTTP Connection Pooling for Salesforce CRM Client (src/clients/salesforce_client.py & src/api/app.py).

What We Built: Refactored SalesforceAsyncClient from allocating throwaway, ephemeral httpx.AsyncClient instances on every individual method call into an enterprise-grade connection-pooled architecture with configurable keep-alive limits, thread-safe lazy instantiation, ownership tracking, and clean FastAPI application lifespan shutdown hooks.

Why We Need It: In high-throughput enterprise travel agent operations, a single user conversation turn triggers 3 to 6 distinct CRM API calls (JWT auth, query ID by name, get booking, get package, patch status). Under the previous implementation, each call performed an isolated TCP connection and full TLS 1.3 handshake, discarding the socket into Linux TIME_WAIT state immediately after. This incurred an unnecessary 150ms+ latency penalty per call and risked fatal OS socket starvation under 50+ req/s load.

Where It Fits in the System: Sits directly beneath the LangGraph Tool layer (src/tools/travel_tools.py and src/tools/salesforce_tools.py), providing persistent, highly concurrent, non-blocking HTTP transport to Salesforce Apex REST and standard REST endpoints.

3. Core Concepts & Fundamentals

1. HTTP Keep-Alive & Connection Pooling

Concept: By default in HTTP/1.1, connections are persistent (Connection: keep-alive). Instead of closing the TCP socket after receiving an HTTP response, the socket is returned to a client-side pool to handle subsequent requests to the same origin host.

Internal Mechanics: The OS socket file descriptor remains open in an established state. When a new request to https://yourdomain.my.salesforce.com is dispatched, the pool checks for an idle socket whose keepalive timeout has not expired and reuses it immediately.

Analogy: Rather than dialing the phone, waiting for the ring, exchanging pleasantries, speaking one sentence, and hanging up, you keep the phone line open and speak whenever you have an update.

2. Ephemeral Port Exhaustion & TIME_WAIT State

Concept: When a TCP connection is closed actively by the client, the OS enters the TIME_WAIT state for 2 * MSL (Maximum Segment Lifetime, typically 60 seconds) to ensure delayed duplicate packets do not corrupt future connections using the same 4-tuple (source IP, source port, dest IP, dest port).

The Bottleneck: The client has a finite pool of outbound ephemeral ports (default Linux: 32768 to 60999 = ~28,232 ports). If requests close connections rapidly, ports remain stuck in TIME_WAIT, leading to complete socket starvation.

3. Client Ownership & Inversion of Control (IoC)

Concept: A client component may either own its internal HTTP client (instantiated by default) or receive an external injected client (e.g. from a test harness or global shared gateway).

Design Rule: The creator owns the resource. If SalesforceAsyncClient instantiates its own httpx.AsyncClient, it is responsible for closing it in aclose(). If an external client was passed in, _owns_client = False, and calling aclose() must not shut down the caller's client.

Step 1: Configure Enterprise Connection Limits

Defined persistent timeouts and pool boundaries in src/clients/salesforce_client.py:

# Connection pool limits for persistent client: keeps connections alive, caps total sockets
_DEFAULT_LIMITS = httpx.Limits(
    max_keepalive_connections=20,
    max_connections=50,
    keepalive_expiry=30.0,
)

Step 2: Add Constructor Injection & Ownership Tracking

Allowed passing an optional external client while defaulting to managed pooling:

def __init__(
    self,
    client_id: str,
    login_url: str,
    private_key_path: str,
    domain: str,
    http_client: Optional[httpx.AsyncClient] = None,
):
    self.client_id = client_id
    self.login_url = login_url.rstrip("/")
    self.domain = domain.rstrip("/")
    self.private_key_path = Path(private_key_path)

    self._private_key = self._load_private_key()
    self._token_cache: dict[str, tuple[str, float]] = {}
    self._client = http_client
    self._owns_client = http_client is None

Step 3: Implement Auto-Healing Property & Clean Teardown

Created the http_client property to instantiate or revive the client on demand, paired with aclose() and context manager protocols:

@property
def http_client(self) -> httpx.AsyncClient:
    """Return active connection-pooled AsyncClient or instantiate on demand."""
    if self._client is None or self._client.is_closed:
        self._client = httpx.AsyncClient(timeout=_TIMEOUT, limits=_DEFAULT_LIMITS)
        self._owns_client = True
    return self._client

async def aclose(self) -> None:
    """Close persistent HTTP client and release connection pool sockets."""
    if self._owns_client and self._client is not None and not self._client.is_closed:
        await self._client.aclose()

async def __aenter__(self) -> "SalesforceAsyncClient":
    return self

async def __aexit__(self, exc_type, exc_val, exc_tb) -> None:
    await self.aclose()

Step 4: Refactor All 11 Ephemeral Invocations

Replaced every async with httpx.AsyncClient(timeout=_TIMEOUT) as client: block across 10 methods and token exchange with direct calls to await self.http_client.get(...) and await self.http_client.patch(...).

Step 5: Integrate with FastAPI Application Lifespan

In src/api/app.py, hooked client disposal to guarantee zero dangling file descriptors on server shutdown:

@asynccontextmanager
async def lifespan(app: FastAPI):
    # Startup phase
    sf_client = get_salesforce_client()
    ...
    yield
    # Shutdown phase
    if sf_client is not None:
        await sf_client.aclose()

8. Internal Working & Code Deep Dive

Pool Parameterization Justification

Setting Value Technical Rationale
max_keepalive_connections 20 Maintains up to 20 idle warm sockets ready for immediate dispatch across concurrent agent threads without renegotiation.
max_connections 50 Strict ceiling on total active TCP sockets. Prevents an unexpected spike in LLM tool execution from flooding Salesforce API limits.
keepalive_expiry 30.0s Salesforce load balancers typically drop idle TCP connections after 60-120s. Setting expiry to 30s guarantees our pool retires idle connections before remote RST packets occur.
timeout 10.0s Ensures hung external Apex scripts do not starve event loop workers indefinitely.

12. Common Mistakes & Troubleshooting

Top Pitfalls in Asynchronous Connection Pooling

  1. Accidentally Closing Injected Clients: If a test passes an existing mock or shared client to SalesforceAsyncClient, calling aclose() on the wrapper could terminate the test runner's client prematurely. Prevention: Enforce self._owns_client flag.
  2. Dangling Sockets on Container Crash: If FastAPI terminates without running lifespan exits, OS sockets linger. Prevention: Always pair with async context manager hooks in app.py.
  3. Stale Socket Remote Reset: Remote Salesforce gateways silently close idle keepalive sockets after 60s. If the client attempts to write on a dead socket, a RemoteProtocolError occurs. Prevention: Set keepalive_expiry=30.0 to proactively refresh sockets before the gateway drops them.

13. Learning & Memory Retention

2-Minute Quick Revision

  • The Rule: Never create an httpx.AsyncClient inside a hot method. Always hold a persistent instance.
  • The Payoff: Saves ~150ms per call by skipping redundant TLS 1.3 handshakes; protects container from TIME_WAIT port exhaustion.
  • The Architecture: Property-based auto-healing lazy getter + ownership flag + FastAPI lifespan teardown hook.

14. Technical Interview Preparation

Senior System Design & Coding Questions

Q1: Why is connection pooling critical in an autonomous agent architecture compared to a traditional web app?
Answer: Traditional web applications typically execute 1 HTTP request per user action. Autonomous ReAct agents execute iterative tool-calling loops where a single user prompt routinely triggers 3 to 8 sequential or parallel downstream API requests. Without pooling, latency compound multiplies handshakes exponentially, making conversational UX unusable.

Q2: What is the risk of setting max_connections too high in httpx?
Answer: Setting an unbound or excessively high connection limit risks flooding the downstream API (Salesforce) with concurrent requests during traffic bursts, resulting in HTTP 429 (Too Many Requests) rate-limiting or IP-level blocking. A strict ceiling (e.g. 50) buffers load and protects external rate quotas.

Q3: How does httpx handle Keep-Alive expiration versus the remote server's idle timeout?
Answer: If the client's keepalive_expiry is higher than the server's idle timeout, the client may attempt to send a request over a socket that the server has already half-closed with a FIN packet. To prevent race conditions and broken pipe errors, the client's keepalive expiry must be set safely lower than the upstream server's timeout.
