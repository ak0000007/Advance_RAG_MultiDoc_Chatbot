Advanced CRAG Architecture: Parallel Per-Chunk Grading & Verifiable Citations

Self-Correcting Retrieval-Augmented Generation, Fine-Grained Filtering & Hallucination Elimination

Section 1: Feature Overview

Subsystem: Retrieval & Generation Pipeline (src/rag/, src/tools/document_search.py, src/retrieval/citations.py)

What We Built: A production-grade Corrective RAG (CRAG) state machine incorporating two mission-critical capabilities:

  1. Parallel Per-Chunk Grading & Filtering: Evaluates each retrieved document chunk independently with a lightweight, structured LLM (ChunkGrade: {is_relevant: bool, reason: str}) via asyncio.gather(). Discards irrelevant chunks completely so only verified text reaches generation. Incorporates a tunable threshold (crag_retry_irrelevance_threshold, default 0.8) that triggers query rewriting and re-retrieval when 4 out of 5 chunks fail relevance.
  2. Inline Per-Claim Citations & Automated Verification: Enforces prompt discipline requiring inline citations in the format [source, page] after every factual claim. A deterministic post-processor inspects the text, matches cited documents and pages against the chunks actually retrieved in that conversation turn, and flags (or drops) any hallucinated citations.
Non-Breaking Invariant: The entire CRAG loop is encapsulated cleanly within the search_documents tool and response generation pipeline. The root LangGraph ReAct engine, Salesforce CRM tools, and Human-in-the-Loop (HITL) approval interrupts remain completely intact and unaffected.

Section 2: Real-World Business Scenario

Enterprise Travel Policy & Cancellation Dispute

The Incident Before CRAG: An executive travel coordinator queried: "What is our penalty policy if an international flight is cancelled due to severe weather?"

The hybrid retriever returned 5 chunks:

  • Chunk 1 (Top score): handbook_holidays.pdf (Irrelevant: Company holiday schedule in December).
  • Chunk 2: domestic_cancellation.pdf (Semi-relevant: $50 fee for domestic tickets).
  • Chunk 3: cafeteria_reimbursement.pdf (Irrelevant: Meal expense caps).
  • Chunk 4: baggage_terms.pdf (Irrelevant: Lost luggage allowances).
  • Chunk 5: international_travel_policy.pdf, Page 9 (Relevant: Severe weather cancellations are 100% refundable without penalty).

The Flaw of Standard RAG: All 5 chunks were bundled into the LLM prompt. The generator hallucinated that a $50 cancellation fee applied and cited a nonexistent document [weather_rules.pdf, page 4]. The company incorrectly penalized the client $500 across 10 tickets.

The Solution with CRAG:

  1. Per-Chunk Grading: 4 out of 5 chunks are graded is_relevant=False in parallel.
  2. Threshold Trigger: Irrelevance ratio is 4/5 = 80% (>= 0.8). Query rewriter rewrites the prompt to: "international flight cancellation severe weather force majeure policy" and re-retrieves.
  3. Second Retrieval: Returns 3 highly specific chunks from international_travel_policy.pdf.
  4. Filtering: Only relevant chunks are fed into generation.
  5. Per-Claim Verification: The answer claims 100% refund citing [international_travel_policy.pdf, page 9]. The validator confirms this chunk was retrieved and stamps it as verified.

Section 3: Core Concepts & Fundamentals

Concept Plain-English Definition Why It Matters How It Operates
Corrective RAG (CRAG) Self-evaluating retrieval architecture that diagnoses retrieval quality before generating answers. Prevents "Garbage In, Garbage Out" where poor retrieval corrupts generation. Scores chunks, filters noise, and triggers query transformation if retrieval confidence is low.
Per-Chunk Grading Evaluating each chunk individually rather than grading the entire concatenated context. In concatenated context, 1 good chunk masks 4 bad chunks, letting noise slip into the generator. Concurrent async LLM calls return boolean relevance decisions per chunk.
Tunable Retry Threshold A configurable ratio (e.g. 0.8) defining how many bad chunks justify a retry. Different enterprise domains tolerate different noise ratios. Hardcoding breaks flexibility. irrelevant_count / total_chunks >= threshold -> triggers rewriter_chain.
Inline Per-Claim Citations Writing [source, page] immediately following the specific factual sentence. Granular attribution allows human auditors to verify every specific claim. Prompt engineering instructs the model to bind claims to bracketed citations.
Automated Citation Verification Deterministic regex parsing and validation against retrieved chunk metadata. LLMs can hallucinate citations (inventing fake document names or page numbers). Compares parsed citations to actual retrieval turn metadata; flags or drops mismatches.

Section 6: Code Deep-Dive (Annotated Line-by-Line)

1. Parallel Chunk Grading & Filtering (src/tools/document_search.py)

# Grade each candidate chunk concurrently using asyncio.gather
async def _grade_single_chunk(document, idx: int):
    xml_entry, _ = format_document_citation(document, idx)
    chunk_text = getattr(document, "page_content", "") or str(document)
    try:
        grade = await grader_llm.ainvoke({
            "question": query,
            "chunk": chunk_text,
            "context": chunk_text,
            "format_instructions": parser.get_format_instructions(),
        })
        return document, grade, xml_entry, None
    except Exception as exc:
        return document, None, xml_entry, exc

# Fire all LLM calls concurrently across the network
graded_results = await asyncio.gather(
    *[_grade_single_chunk(doc, idx) for idx, doc in enumerate(documents, start=1)]
)

relevant_entries = []
irrelevant_entries = []
for doc, grade, xml_entry, exc in graded_results:
    if exc is not None:
        # Fail-open resilience: retain chunk if LLM fails
        relevant_entries.append((doc, xml_entry))
        continue
    if getattr(grade, "is_relevant", getattr(grade, "relevant", True)):
        relevant_entries.append((doc, xml_entry))
    else:
        irrelevant_entries.append((doc, grade))

irrelevance_ratio = len(irrelevant_entries) / len(documents)
should_retry = (len(relevant_entries) == 0) or (irrelevance_ratio >= irrelevance_threshold)

if not should_retry and relevant_entries:
    # PASS ONLY RELEVANT CHUNKS TO GENERATOR!
    return "\n\n".join([xml for _, xml in relevant_entries])

_INLINE_CITATION_RE = re.compile(
    r'\[(?:Doc:\s*)?([^,\]\n]+?)(?:,\s*(?:[Pp]age\s*|[Pp]\.?\s*)?(\d+))?\](?!\()',
    re.IGNORECASE,
)

def verify_and_filter_inline_citations(text: str, retrieved_citations: list[dict], mode: str = "flag"):
    # Normalizes source, title, chunk_id and verifies page compatibility
    def _replace_match(match: re.Match) -> str:
        source_raw = match.group(1).strip()
        cited_page = int(match.group(2)) if match.group(2) else None
        
        # Check against retrieved chunks in this turn
        matched = find_retrieved_match(source_raw, cited_page, retrieved_citations)
        if matched:
            return match.group(0)  # Preserved as VERIFIED
            
        if mode == "drop":
            return ""  # Stripped completely
        return f"[UNVERIFIED CITATION: {source_raw}]"  # Flagged loudly for audit

Section 10: System Design Defenses & Trade-offs

Key Design Decisions

1. Tool-Level Encapsulation vs Top-Level LangGraph Nodes:

  • Trade-off: Putting CRAG as 4 top-level LangGraph nodes creates a rigid pipeline that breaks the ReAct agent. The system could no longer choose between CRM tools and document search, breaking Salesforce read/write and HITL approval.
  • Defense: Encapsulating CRAG inside search_documents maintains clean ReAct architecture. The agent invokes search_documents as an intelligent tool that internally executes retrieval, grading, rewriting, and filtering.

2. Parallel Async Execution (asyncio.gather):

  • Trade-off: Running 5 grading calls sequentially adds ~2.5 seconds of latency (5 x 500ms).
  • Defense: Running 5 calls concurrently in parallel takes ~550ms total, minimizing latency impact while maximizing filtering precision.

Section 12: Beginner-Friendly Mental Models

The Airport Security Checkpoint Analogy

Imagine your retrieval pipeline is an international airport security checkpoint:

  • Hybrid Retrieval (RRF): The bus brings a group of 5 passengers (chunks) to the gate.
  • Per-Chunk Grading: Rather than looking at the group as a whole, 5 security agents inspect each passenger's passport simultaneously. 4 passengers have invalid documents.
  • The Retry Rule: Because 80% of the passengers failed inspection, the supervisor rejects the bus and radios dispatch (Query Rewriter) to send a properly vetted bus.
  • Filtering: Only verified passengers are allowed onto the airplane (Generation). The 4 rejected passengers are left behind.
  • Citation Verification: When a passenger claims they are in Seat 3A, the flight attendant checks the boarding pass against the passenger manifest. If the seat or name is fabricated, an alert is raised.

Section 13: Memory Aids & Cheat Sheets

CRAG Invariants Rulebook

  • P — Parallel: Never grade chunks serially. Always use asyncio.gather().
  • F — Filter: Never let irrelevant chunks reach the prompt. Pass ONLY relevant chunks.
  • T — Tunable: Never hardcode the retry ratio. Use settings.crag_retry_irrelevance_threshold.
  • V — Verify: Never trust generated citations blindly. Match against retrieved chunks.
  • S — Safe Fallback: Never crash on grader failure. Fail-open with unverified banners.

Section 14: Comprehensive Interview Preparation Guide

Q1: What is the core difference between standard RAG, Self-RAG, and Corrective RAG (CRAG)?

Answer: Standard RAG naively passes retrieved chunks straight to generation. Self-RAG uses reflection tokens to assess generation quality after output. Corrective RAG (CRAG) evaluates retrieval quality before generation by grading chunks, discarding irrelevant noise, and triggering automated query rewriting when retrieval quality falls below a defined threshold.

Q2: Why grade chunks individually rather than grading the whole retrieved context?

Answer: When grading concatenated context, the presence of a single highly relevant chunk often causes the LLM to score the entire context as relevant, allowing irrelevant or contradictory chunks to remain. These irrelevant chunks confuse the generator, cause hallucinations, or leak outdated policy rules. Per-chunk grading isolates each chunk, ensuring that noisy chunks are surgically filtered out.

Q3: How do you prevent LLMs from hallucinating source citations?

Answer: Prompt engineering alone cannot prevent citation hallucination. In our architecture, we combine prompt discipline with a deterministic post-processor (verify_and_filter_inline_citations). It parses inline tags like [doc, page] and checks them against the metadata of chunks retrieved in the current turn. Hallucinated citations are either converted to [UNVERIFIED CITATION: ...] or dropped from the text.

Q4: Why not model the 4 CRAG steps as top-level LangGraph nodes?

Answer: In an enterprise agent that handles both corporate documents and CRM operations (Salesforce Bookings, Payments, Opportunities), the top-level graph must be a flexible ReAct agent. Modeling CRAG as fixed top-level graph nodes makes the workflow rigid and prevents the agent from choosing between CRM actions and document retrieval. Encapsulating CRAG inside the search_documents tool delivers self-correcting retrieval without sacrificing agent flexibility or human-in-the-loop approval.
