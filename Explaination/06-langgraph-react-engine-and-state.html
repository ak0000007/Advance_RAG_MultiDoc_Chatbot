Module 06: LangGraph ReAct Engine, State Management & Memory Checkpointing

Cyclic Graph Orchestration, Additive Message Reducers & Persistent Database Checkpointing

1. State Machines vs Linear Chains

Traditional LLM frameworks rely on linear chains (DAGs or LCEL pipelines). Linear chains assume a deterministic sequence: 

Input → Prompt → LLM → Output

Real enterprise tasks are rarely linear. If a user asks: "Find my booking for Bali and change the date to Nov 15", the system must:

  1. Plan and call get_booking.
  2. Evaluate the returned booking details.
  3. Plan and call update_booking.
  4. Pause for human approval via an interrupt.
  5. Resume and complete synthesis after approval.

LangGraph StateGraph models this as a cyclic state machine where nodes return partial state dictionaries, and conditional edges decide which node to visit next.

2. RAGState & Additive Message Reducer

The central state dictionary is RAGState (in src/graph/state.py). A critical feature is the add_messages reducer: 

class RAGState(TypedDict, total=False):
    # 'add_messages' is a reducer: rather than replacing the message list,
    # it intelligently appends new messages and updates existing ones matching by ID.
    messages: Annotated[list[Any], add_messages]
    question: str
    history: list[Any]
    rewritten_query: str
    documents: list[Any]
    citations: list[dict[str, Any]]
    
    # Safety and Context Invariants
    write_count: int      # Incremented on approved mutations; capped by session limit
    sf_username: str      # Persisted across async interrupts and resume turns
    tenant_id: str        # Persisted multi-tenant isolation context

4. PostgreSQL Persistence Checkpointing

To support async human approval and multi-turn conversational memory across server restarts, the graph state is persisted to PostgreSQL using AsyncPostgresSaver.

  • Checkpoints Table: Stores binary serialized state snapshots keyed by (thread_id, checkpoint_ns, checkpoint_id).
  • Writes Table: Logs pending and committed state mutations per step.
  • Connection Pool Lifecycle: Managed via AsyncConnectionPool, opened during FastAPI app lifespan and gracefully drained on shutdown.

5. Code Implementation Deep-Dive (src/graph/graph.py)

def _after_tool_router(state: RAGState) -> str:
    """Route to human_approval if any mutating tool returned __requires_approval__."""
    messages = state.get("messages", [])
    if not messages:
        return "agent"

    last_msg = messages[-1]
    if isinstance(last_msg, ToolMessage):
        try:
            content = json.loads(last_msg.content)
            if isinstance(content, dict) and content.get("__requires_approval__"):
                return "human_approval"
        except (json.JSONDecodeError, TypeError):
            pass

    return "agent"

def build_rag_graph(tools, llm, checkpointer=None, pool=None):
    workflow = StateGraph(RAGState)

    agent = build_agent_node(llm, tools)
    tool_node = ToolNode(tools)
    approval_node = build_human_approval_node(pool=pool)

    workflow.add_node("agent", agent)
    workflow.add_node("tools", tool_node)
    workflow.add_node("human_approval", approval_node)

    workflow.add_edge(START, "agent")
    workflow.add_conditional_edges(
        "agent",
        tools_condition,  # Built-in: checks if last message has tool_calls
        {"tools": "tools", END: END},
    )
    workflow.add_conditional_edges(
        "tools",
        _after_tool_router,
        {"human_approval": "human_approval", "agent": "agent"},
    )
    workflow.add_edge("human_approval", "agent")

    return workflow.compile(checkpointer=checkpointer)

6. Senior Engineering Interview Defense

Q1: How does LangGraph handle message list growth over a 50-turn conversation?

Answer: Using add_messages reducer, each state transition appends new messages or updates existing messages if an ID matches. For long-running conversations that threaten the LLM context window, we can configure a message trimmer (such as trim_messages) or windowing strategy before passing state to the LLM agent node, while preserving the full authoritative history in PostgreSQL checkpoint records.

Q2: What is the difference between LangGraph MemorySaver and AsyncPostgresSaver?

Answer: MemorySaver stores checkpoint dictionaries in volatile RAM. It is ideal for unit tests and local mock development, but any process restart or container redeployment wipes all conversation memory. AsyncPostgresSaver commits binary checkpoint blobs to PostgreSQL tables, providing ACID durability, multi-pod horizontal scalability, and persistent threads across long-lived async approvals.
