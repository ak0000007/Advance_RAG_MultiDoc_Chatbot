Statistical IR Metrics, 4-Pipeline Benchmarking, LLM Judges & Multi-Tracer Distributed Telemetry

1. Why Evaluation is Mandatory (Moving Beyond "Vibe Checks")

Most RAG applications are evaluated via subjective "vibe checks" — developers manually ask three questions and assume the system works. In production:

  • Changing chunk size from 1000 to 800 may silently break retrieval for complex multi-paragraph policies.
  • Swapping an embedding model may boost Hit@1 on definitions while destroying recall on tables.
  • Prompt changes can cause the LLM to hallucinate answers instead of abstaining when questions are unanswerable.
Objective Evaluation: We built an automated evaluation harness in evals/rag/ with statistical IR metrics and an LLM judge to benchmark retrieval pipelines deterministically in CI/CD.

2. Core Statistical Retrieval Metrics (evals/rag/metrics.py)

MetricDefinitionWhat It Measures
Hit@k 1 if at least one relevant document appears in top-k results; 0 otherwise. Was the user's answer present in the retrieved set at all?
Recall@k |Retrieved Relevant Docs| / |Total Ground Truth Relevant Docs|. Did the system find all pieces of evidence needed for multi-doc synthesis?
MRR (Mean Reciprocal Rank) 1 / rank_first_relevant averaged across all benchmark queries. How close to the very top (rank 1) is the first relevant piece of evidence?
nDCG@k Normalized Discounted Cumulative Gain: DCG / IDCG. Are highly relevant documents ranked ahead of moderately relevant ones?

Zero Chunk ID Churn

A common flaw in RAG benchmarks is hardcoding chunk IDs in the evaluation dataset. Whenever an engineer changes chunk overlap, all chunk IDs change, breaking the entire test set.

Our evaluation harness matches against normalized source file names and substring contains checks. You can re-chunk, re-index, or change document boundaries without breaking your golden dataset!

4. LLM Judge & Faithfulness Evaluation

Passing the --judge flag activates an LLM evaluation stage that assesses:

  1. Faithfulness: Does the generated answer contain claims not supported by the retrieved context? (Score 0.0 to 1.0).
  2. Abstention on Unanswerable Queries: For questions where ground truth is missing (e.g. "What is the SpaceX Mars flight code?"), did the model correctly state that the policy does not contain this information rather than hallucinating?

6. Code Implementation Deep-Dive (evals/rag/metrics.py)

def is_chunk_relevant(doc: Document, target_sources: Sequence[str], contains_phrases: Sequence[str]) -> bool:
    """Evaluate relevance without hardcoding volatile chunk IDs."""
    doc_source = normalize_filename(doc.metadata.get("source", "") or doc.metadata.get("file_name", ""))
    target_normalized = {normalize_filename(s) for s in target_sources}

    if target_normalized and doc_source not in target_normalized:
        return False

    content_lower = doc.page_content.lower()
    for phrase in contains_phrases:
        if phrase.lower() not in content_lower:
            return False
    return True

def compute_retrieval_metrics(retrieved_docs: Sequence[Document], target_sources: Sequence[str], contains: Sequence[str], k_values=(1, 3, 5)) -> dict:
    hits = [is_chunk_relevant(d, target_sources, contains) for d in retrieved_docs]
    
    # Calculate MRR
    first_hit_rank = next((idx for idx, hit in enumerate(hits, start=1) if hit), None)
    mrr = (1.0 / first_hit_rank) if first_hit_rank is not None else 0.0

    metrics = {"mrr": mrr}
    for k in k_values:
        sub_hits = hits[:k]
        metrics[f"hit@{k}"] = 1.0 if any(sub_hits) else 0.0
        metrics[f"recall@{k}"] = sum(sub_hits) / len(target_sources) if target_sources else 1.0
        metrics[f"ndcg@{k}"] = compute_ndcg(sub_hits, k)
    return metrics

7. Senior Engineering Interview Defense

Q1: Why should an enterprise RAG evaluation avoid binding to static chunk IDs?

Answer: Chunk IDs are volatile artifacts of the preprocessing pipeline. If an engineer tunes the chunk size, updates the markdown parser, or adds a single sentence to a policy document, every single downstream chunk ID changes. If the evaluation dataset contains hardcoded chunk IDs, the entire benchmark becomes invalid overnight. By matching on normalized source files and semantic phrase presence, the evaluation dataset remains a durable, long-term gold standard.

Q2: How do you measure hallucination in an automated CI/CD pipeline?

Answer: We use a two-pronged approach. First, we compute retrieval precision (Hit@k, MRR) to ensure that ground-truth context is actually fed to the generator. Second, we run an LLM judge with structured output that decomposes the generated answer into atomic claims, checking whether each claim is supported by the retrieved context chunks (Faithfulness score). For unanswerable adversarial queries, the judge verifies that the model explicitly abstains.
