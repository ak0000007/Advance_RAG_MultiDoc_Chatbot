Module 04: Cross-Encoder Reranking & Retrieval Calibration

Deep Token-to-Token Cross-Attention for High-Precision Document Candidate Re-Scoring

1. Bi-Encoder vs Cross-Encoder (The Fundamental Difference)

Information retrieval systems face a classic trade-off between computational efficiency and semantic precision:

Attention MechanismOnly self-attention within Query; only self-attention within DocFull all-to-all cross-attention between every query token and document token

2. Two-Stage Retrieval Architecture

We use a standard two-stage funnel:

  1. Stage 1 (High Recall): HybridRetriever queries Qdrant and BM25 in parallel to retrieve the top 20 candidate chunks. Cost: ~15ms.
  2. Stage 2 (High Precision): CrossEncoderReranker scores all 20 pairs using bge-reranker-v2-m3, filtering and sorting down to the top 5 highest-confidence chunks. Cost: ~35ms.

3. Thread Safety & Async Non-Blocking Execution

Heavy PyTorch models can cause concurrency bugs in async web frameworks like FastAPI:

  • Race Conditions on Model Load: If two requests hit an uninitialized lazy singleton at the same millisecond, both threads attempt to allocate ~1.5GB of GPU/RAM. We guard initialization with asyncio.Lock().
  • Event Loop Starvation: Running model.predict() directly inside an async coroutine blocks the FastAPI event loop for 40ms, causing incoming HTTP requests to stall. We offload inference to worker threads via asyncio.to_thread().

4. Threshold Calibration & Confidence Gating

A reranker that returns irrelevant documents with low confidence causes LLM hallucinations. We calibrate relevance gating via two settings:

  • settings.retrieval_confidence_threshold = 0.7: Documents scoring below 0.7 are pruned.
  • settings.retrieval_min_confident_docs = 3: If fewer than 3 documents exceed the confidence threshold, the retriever signals potential retrieval failure, triggering query rewriting.

5. Implementation Deep-Dive (src/reranking/reranker.py)

class CrossEncoderReranker:
    def __init__(self, model_name: str = "BAAI/bge-reranker-v2-m3"):
        self.model_name = model_name
        self._model = None
        self._lock = asyncio.Lock()

    async def _get_model(self):
        """Thread-safe lazy initialization using asyncio.Lock."""
        if self._model is None:
            async with self._lock:
                if self._model is None:
                    # Offload heavy model loading to thread pool
                    self._model = await asyncio.to_thread(
                        CrossEncoder, self.model_name, trust_remote_code=True
                    )
        return self._model

    async def arerank(
        self,
        query: str,
        documents: list[Document],
        top_k: int = 5,
    ) -> list[Document]:
        if not documents:
            return []

        model = await self._get_model()
        pairs = [(query, doc.page_content) for doc in documents]

        # Non-blocking CPU/GPU inference via asyncio.to_thread
        raw_scores = await asyncio.to_thread(model.predict, pairs)
        scores = [float(s) for s in raw_scores]

        scored_docs = list(zip(documents, scores))
        # Sort descending by cross-encoder score
        scored_docs.sort(key=lambda x: x[1], reverse=True)

        return [doc for doc, score in scored_docs[:top_k]]

7. Senior Engineering Interview Defense

Q1: Why can't we use a Cross-Encoder as our primary retrieval engine?

Answer: Cross-Encoders do not produce standalone document embeddings that can be pre-computed and stored in an HNSW index. In a Cross-Encoder, the query and document tokens must be concatenated and fed together into the attention layers. Searching a million documents would require a million forward passes for a single user query, which is computationally prohibitive. Hence, we use Bi-Encoders for fast candidate retrieval (top-20) and Cross-Encoders for precise reranking (top-5).

Q2: How do you prevent event loop blocking when running PyTorch inference in an async FastAPI service?

Answer: PyTorch inference (`model.predict()`) is CPU/GPU-bound synchronous code. If executed directly inside an async route or tool, it blocks the single-threaded asyncio event loop, preventing FastAPI from processing any other incoming HTTP requests. We wrap the inference call in await asyncio.to_thread(model.predict, pairs), delegating execution to the default thread pool executor while freeing the event loop.
